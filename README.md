# Mastering Shiny - Chapter 4 - Case Study: ER injuries  
This repository contains scripts generated by following the instructions found in Mastering Shiny, Chapter 4 (as accessed in August 2026). The original script, generated by working through the chapter step-by-step is saved under `app_original.R`. The version containing solutions to the exercise is saved under `app.R`. 

### Source: [https://mastering-shiny.org/basic-case-study.html](https://mastering-shiny.org/basic-case-study.html)    
This app from Chapter 4 of Hadley Wickham's "Mastering Shiny" summarises data as collected through the National Electronic Injury Surveillance System (NEISS) in 2017. The primary aim of NEISS is to collect data on consumer product-related injuries occurring in the United States. The data is obtained from a nationally representative probability sample of hospitals in the U.S. and its territories. One of the more interesting aspects of this data is that each entry is accompanied by a "narrative" that describes the context surrounding the injury. This gives deeper insight into the reasons behind product-related injuries.  The data can also be split by age and sex to identify trends relating to these factors.

The exercise at the end of the chapter instructs the learner to:  

1. Add an input control that allows the user to select how many rows to show in the summary tables.
2. Provide a way to step through every narrative relating to that specific class of injury, with a bonus challenge of making the list of narratives "circular" so that advancing forward from the last narrative takes you to the first.

I completed point 1 fairly easily by swapping the tableOutput UI objects to DataTable (DT) objects and "switching off" the built-in search function. Point 2 required a couple of hours of thinking and considering. I also wanted to know how ChatGPT would have solved this problem after I'd already had a go, so below I paste two LLM solutions from ChatGPT: one from 12 August 2026 where it created a button that would go forward and backward, but not loop, and one from 17 August 2026 where it loops using modulo. I also compare what the LLM did with how I figured it out on my own.

### Adding buttons that increment one narrative forwards or backwards on clicking, and loops around  
First, I changed the UI to have two buttons. A fluidRow is 12 units wide, so the sum total of the column widths have to be adjusted. Pretty straightforward (and identical to what the LLM suggested when I asked).    
<img src="https://github.com/PlantsGenesBugs/ER_injuries/blob/main/images/button_forw_back.png" alt="Snapshot of UI code used to generate two buttons to move one narrative forwards or backwards when clicked." width="600">

Then I changed the server function to respond correctly when the previous/next buttons are clicked. I approached this as if it were a `for` loop in the first instance, so that you'd initialise an index value at the start, and increment it every time the loop runs (or, in this case, the button is clicked). In the Shiny universe, this consists of a reactive value (box labelled `1` below). Once I'd done this, I wanted to make sure that there is already a narrative visible (index position 1) when the user has selected a product from the drop-down list (box labelled `2` below). The easier button to define at this point was the next button (box labelled `3`), where, if the user clicked on the "Next story" button (`input$next_narr`), the click would increment the index value by one, check if the next position would be one step beyond the last narrative story, and, if so, set the index value to 1, otherwise move the index value up one spot. Alternatively, when clicking on the "Previous story" button (`input$prev_narr`), if the current position is 1, then the index should move to the last story in the selection, otherwise the index should just decrease by 1. The selection index value is used to pull a sentence from the column of narratives, where the index value specifies the row number from that column to show in the UI (box labelled `4`).

### ChatGPT solution: no "circular" story selection  
ChatGPT sets an index (line 13) and ensures that a narrative story is shown once the user selects a product from the drop-down list (lines 14-15). In line 19, the variable `n` is defined as the number of rows in the subset of rows selected from the original data frame. This isn't strictly necessary (the code will run without it), but a general rule of thumb in coding is that, when code is repeated 2 or 3 times, the repeated code can be contained in a variable (or for loop) to tidy the script up, and that is why this has happened here. The variable `n` is used in line 21 and line23, and makes the code more readable. However, since `nrow(selected())` is only used once in the code defining observeEvent() for the Previous Story button (`input$story_prev`), it is not assigned to a variable here.

If the user clicks on "Next story", and the subset of data contains any rows (line 21), the narrative index value is set to whichever is the smallest value (`min`) between the current index +1, or the number of rows in the subset (line 23). So even if the user clicks on the button repeatedly, the narrative_index value will never go above the last row of the subset at hand. Similarly, when the user clicks on the "Previous story" button (line 28), if there is any data in that selection (line 29), the index decreases by one value, unless that value would fall below 1, in which case the index is set to 1 and the first row in the subset is returned (line 31).

### ChatGPT solution: circular story selection  
As with my own code, ChatGPT created a reactive value that serves as an index for the subset of narratives relating to the selected product (box labelled `1` below). It also ensures that the first narrative in the selection is displayed when a user makes a selection (box labelled `2` below). However, while my code refers to the `selected()` reactive expression (see box `2` in my own server function above), ChatGPT uses the object `input$code` as first argument. `input$code` represents the drop-down list in the UI that contains all of the products. If this changes, then the narrative will change. In my code, the narrative relies on the `selected()` reactive expression running. I chose to use `selected()` because it was more in line with the code that relates to changes when the user clicks on the Previous and Next buttons. But relating it to `input$code` is certainly not wrong. The server function for when the Previous and Next buttons are clicked are defined in the opposite sequence by ChatGPT (Next button first). The order of the code here doesn't matter, but I did Previous first since it's the first button that appears in the UI. The biggest difference between my code and ChatGPT's is how ChatGPT manages the change in index value (box labelled `3` below). For the Next button, the new `narrative_index` is calculated by taking the current index and returning the remainder after dividing by the number of rows (modulo calculation), and then adding 1. For example, if there are 8 rows and the current index is 4, narrative_index %% n + 1 = 4 %% 8 +1 = 4 + 1 = 5. If we're at the last row in the subset, and narrative_index == n, then the modulo operation returns 0 and adding 1 returns us to the first index. For the Previous button, the code first subtracts 2 from the current index, before performing the modulo calculation and adding 1. For example, if we're again on index 4 in a subset with 8 rows, clicking "Previous" calculates (4-2) %% 8 + 1 = 3.   
<img src="https://github.com/PlantsGenesBugs/ER_injuries/blob/main/images/chat_loop.png" alt="" width="600">  

The underlying logic of the addition and subtraction around the modulo function has to do with the fact that R is 1-based and the modulo function is zero-based. This is easier to explain when looking at the server code for the "Previous" button. In line 30, 1 is subtracted from the current index to convert to 0-base, and another 1 is subtracted to move the index one position lower from the current index value. A value of 1 is added at the end of that line to re-convert to 1-base. And so, what is actually happening in the "Next" button server code (line 19) is that 1 is subtracted from the current index to convert to 0-base, and 1 is immediately added again to increment the index value to the next position, leaving us with just the current index. A value of 1 is added again to re-convert to base-1. To note, also, that modulo behaves somewhat unusually with negative numbers, and that this behaviour is also programming language dependent.
